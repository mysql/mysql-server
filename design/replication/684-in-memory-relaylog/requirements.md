### Functional Requirements

- FR1. The feature must provide a per-channel option, introduced as a new `CHANGE REPLICATION SOURCE TO` (CRST) option `IN_MEMORY_RELAYLOG_ENABLED`, that controls whether the feature is enabled. It is `ON` by default for eligible channels. When `OFF`, replication must fall back to the standard disk path relaylog.
- FR1.1. On a channel that is on the classic applier (MTA), the feature is never active, whatever its `IN_MEMORY_RELAYLOG_ENABLED` setting.
- FR1.2. When a new channel is created with a CRST statement, the server must set `IN_MEMORY_RELAYLOG_ENABLED = ON` by default, except when: (1) the CRST statement sets `IN_MEMORY_RELAYLOG_ENABLED` explicitly; or (2) the channel (`group_replication_applier`) is not supported by the feature.
- FR1.3. The server must persist the channel's in-memory relaylog configuration (`IN_MEMORY_RELAYLOG_ENABLED`, `IN_MEMORY_RELAYLOG_LIMIT` and `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD`) and keep it until a CRST statement sets it.
- FR1.4. While the receiver or applier thread runs, a CRST statement that enables/disables the feature must fail with `ER_REPLICA_CHANNEL_MUST_STOP` and leave the channel's configuration unchanged.
- FR2. The feature must only apply to CSA channels with asynchronous replication. Enabling the feature on any unsupported channel type must be rejected with a clear error.
- FR2.1. A CRST statement that sets `IN_MEMORY_RELAYLOG_ENABLED`, `IN_MEMORY_RELAYLOG_LIMIT` or `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD` must fail with `ER_CRST_IN_MEMORY_RELAYLOG_ONLY_FOR_CSA` if the channel is not on CSA after the statement. The error message must be "The in-memory relay log is only available on a CSA-enabled channel." The statement fails before it changes anything, so the channel's configuration is left unchanged.
- FR2.2. A CRST statement that sets `IN_MEMORY_RELAYLOG_ENABLED = ON` on the `group_replication_applier` channel must fail with `ER_REPLICA_IN_MEMORY_RELAYLOG_INCOMPATIBLE_CONFIGURATION`. The error message must be "The in-memory relay log is incompatible with %s and cannot be used while it is active.", with `%s` = "the group_replication_applier channel". The statement fails before it changes anything, so the channel's configuration is left unchanged.
- FR2.3. When the feature is enabled on a channel with `rpl_semi_sync_replica_enabled = ON`, `START REPLICA` and `START REPLICA IO_THREAD` must fail with `ER_REPLICA_IN_MEMORY_RELAYLOG_INCOMPATIBLE_CONFIGURATION`. `START REPLICA SQL_THREAD` is not affected. The CRST statement that enables the feature is not rejected, because semisync can be switched on or off between CRST statements. The error message must be the FR2.2 message with `%s` = "semi-synchronous replication". `START REPLICA` fails before the receiver starts, and queued transactions are kept.
- FR2.4. If semisync is enabled after the receiver has started, the receiver must check again before each binlog dump request (when replication starts with the server, and on every reconnect). It must stop with the FR2.3 error, reported through `Last_IO_Errno` / `Last_IO_Error`.
- FR3. The feature must store each event in the same encoded bytes as in the disk path relaylog, so that the existing decode and apply path can continue working without modification.
- FR4. The receiver must deliver every received transaction to the applier through the channel's in-memory queue, and must not write transaction events to the channel's relaylog files.
- FR4.1. The applier must start applying a transaction after the receiver has received any events from the source.
- FR4.2. The applier must not commit a transaction until the receiver has received all of its events.
- FR4.3. Upon receiving a new transaction, the receiver must select the store path for the payload by comparing the transaction size with the configured `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD`. A transaction with its size exceeding the threshold takes the spill path. Otherwise, it takes the memory path.
- FR5. The feature must not change receiver-side GTID tracking. (1) A GTID must be added to `Retrieved_Gtid_Set` only after the transaction has been marked as sealed; (2) A GTID must be added to `gtid_executed` only after the transaction has been committed by the applier.
- FR6. The CSA applier must process and apply the transactions through the in-memory queue in the same manner as the existing disk path relaylog.
- FR7. The queue must be a per-channel, in-memory data structure that holds transaction envelopes in receiver insertion order. Envelopes are dequeued in FIFO (First-In, First-Out) order.
- FR8. The queue must maintain a per-channel memory-usage counter that tracks the total bytes currently held by memory path transaction envelopes.
- FR8.1. The counter is an atomic variable. It increases by the transaction's size when a memory path payload is created, and decreases by the same amount when that payload is released at commit.
- FR9. The queue must be tracked by three cursors: (1) A commit cursor that marks the last contiguously committed transaction, meaning all transactions before this cursor have been committed with no gaps. (2) A dispatch cursor that marks the next available transaction envelope to be dispatched. (3) An insert cursor that marks the position where the next incoming envelope should be appended.
- FR9.1. The cursors must strictly follow the invariant: `commit cursor` <= `dispatch cursor` <= `insert cursor`.
- FR10. The queue must support concurrent access by the receiver, enqueueing at the tail, and by the coordinator and workers, reading from the head. Each transaction envelope is retained from the time its GTID event is received until it is dequeued after its transaction commits.
- FR10.1. The queue must be protected by a queue-level mutex that guards its structure. All operations that mutate the queue structure and the cursors must hold this mutex.
- FR11. When the queue is empty, the coordinator must wait until the receiver enqueues a new transaction envelope before resuming dispatching.
- FR12. The feature must enforce a hard per-channel memory limit, `IN_MEMORY_RELAYLOG_LIMIT`, on the bytes held by memory path transaction envelopes. The value defaults to 134217728 bytes (128 MB) with a valid range [33554432 bytes (32 MB), 4294967295 bytes (4 GB - 1 byte)].
- FR13. The feature must guarantee that a memory path transaction is known to fit within the memory limit at the GTID event before any of its body is buffered. If there is not enough memory available, the receiver must block until committing transactions free enough memory.
- FR14. When a transaction commits, its memory path transaction payload must be freed. The per-channel memory-usage counter must be decreased by the freed bytes, releasing the memory back at commit time.
- FR15. The feature must store a transaction through the spill path instead of the memory path when its `trx_length` exceeds a configurable per-channel threshold, `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD`. The value defaults to 16777216 bytes (16 MB) with a valid range [8388608 bytes (8 MB), `IN_MEMORY_RELAYLOG_LIMIT`).
- FR16. When a CRST statement sets `IN_MEMORY_RELAYLOG_LIMIT`, `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD`, or both, the server must reject it with `ER_CRST_IN_MEMORY_RELAYLOG_INVALID_CONFIG` and leave both settings unchanged if any of these rules is broken: (1) A new `IN_MEMORY_RELAYLOG_LIMIT` must be between 33554432 bytes (32 MB) and 4294967295 bytes (4 GB - 1 byte). (2) A new `IN_MEMORY_RELAYLOG_SPILL_THRESHOLD` must be at least 8388608 bytes (8 MB). (3) The threshold must be less than the limit. If the statement sets only one of the two options, the server compares it with the channel's current configuration value. (4) A value of 0 for IN_MEMORY_RELAYLOG_LIMIT or IN_MEMORY_RELAYLOG_SPILL_THRESHOLD in a CRST statement is treated as if the option were not supplied.
- FR16.1. The error message must be "Invalid in-memory relay log configuration: %s", where `%s` names the broken rule, N is the effective limit and M is the effective threshold: rule (1) "IN_MEMORY_RELAYLOG_LIMIT (N bytes) must be between 33554432 and 4294967295 bytes"; rule (2) "IN_MEMORY_RELAYLOG_SPILL_THRESHOLD (M bytes) must be at least 8388608 bytes"; rule (3) "IN_MEMORY_RELAYLOG_LIMIT (N bytes) must be greater than IN_MEMORY_RELAYLOG_SPILL_THRESHOLD (M bytes)". The statement fails before it changes anything.
- FR17. The feature must store spill files in a dedicated subdirectory named `#in_memory_relaylog_temp_files` under the channel's relaylog directory. Files must be written in standard relaylog format so that the store is self-contained and on the same filesystem as standard relaylog files.
- FR18. The feature must create the `#in_memory_relaylog_temp_files` directory at server initialization after the relaylog directory is known.
- FR18.1. If the `#in_memory_relaylog_temp_files` directory already exists at startup, the server must clean up its managed temp files according to FR25. This is safe because the channel invalidates and discards all previously fetched relaylog content and recovers solely by GTID auto-positioning based on `gtid_executed`.
- FR18.2. At startup, if the `#in_memory_relaylog_temp_files` path exists but is not a directory, or if directory creation fails or the server lacks read, write and search permission on it, the feature must log a clear error message and reject starting replication channels with `IN_MEMORY_RELAYLOG_ENABLED` set to `ON`. `START REPLICA` on such a channel must fail with `ER_REPLICA_IN_MEMORY_RELAYLOG_SPILL_STORAGE_UNUSABLE`.
- FR18.3. The error message must be "The in-memory relay log cannot be used on channel '%.192s': %s. Check the error log.", with the channel name and `%s` = "the spill directory is not a usable directory". `START REPLICA` of either thread fails before the threads start. The problem is reported only in the server error log.
- FR19. The feature must exclude the `#in_memory_relaylog_temp_files` directory from schema-visible listings such as `SHOW DATABASES` and `information_schema`, so that it does not appear as a schema.
- FR20. Spill path transactions count against `relay_log_space_limit` by their declared size (trx_length) while their spill files exist, as a soft limit. The receiver finishes writing the current transaction's spill file even if the total exceeds the limit, then blocks the next spill path transaction until committed transactions' files are deleted and the total drops back under the limit. A spill file whose run-time delete failed stops counting toward this limit.

- FR21. The spill path file store must use exactly one self-contained file per transaction with a unique filename to avoid conflicts. The file must be deleted automatically once its transaction commits.
- FR21.1. If the server cannot delete a spill file at run time, it must log a warning naming the file and the error, and stop the applier with `ER_REPLICA_RELAY_LOG_READ_FAILURE`, as the server does when it cannot purge a relaylog file.
- FR21.2. After a spill file delete fails at run time, the file no longer counts toward the spill limits or the spill status values. `START REPLICA SQL_THREAD` clears the error flag and starts the applier again, and a server restart deletes the file during the startup cleanup (FR28).
- FR22. A spill file must be created with the same file permissions, ownership, and encryption as the channel's relaylog files, since it contains equally sensitive data and resides alongside the relaylog.
- FR23. If the disk is full while the receiver writes a spill file, the receiver must wait for free space as it does for the relaylog: the IO thread state is "Waiting for disk space", `SHOW REPLICA STATUS` does not block, and writing resumes when space is freed.
- FR24. A spill path temp file created by the feature must have a name matching the pattern `imr_sp_<channel>_<unique_id>`, or `imr_sp_<unique_id>` for the default channel, where `<channel>` is the channel name encoded in the filename character set, as in relay log file names, and `<unique_id>` is a lowercase hexadecimal identifier unique within #in_memory_relaylog_temp_files (IMR SP stands for "In-Memory Relaylog Spill Path").
- FR25. Startup cleanup must delete only spill files whose basename matches the temp file naming pattern `imr_sp_*` and must reject all other directory entries.
- FR26. If startup cleanup cannot read the `#in_memory_relaylog_temp_files` directory or delete a file, the server must log an error and reject starting replication channels with `IN_MEMORY_RELAYLOG_ENABLED` set to `ON`. A file that cannot be deleted is logged as `ER_BINLOG_CANT_DELETE_FILE` from `MYSQL_BIN_LOG`. `START REPLICA` on such a channel must fail with `ER_REPLICA_IN_MEMORY_RELAYLOG_SPILL_STORAGE_UNUSABLE` until the server is restarted with the problem fixed.
- FR26.1. The error message must be the FR18.3 message with `%s` = "stale spill files could not be deleted at server startup". If both FR18.2 and FR26 apply, the FR18.3 reason is reported, because the unusable directory is the root cause.
- FR27. When both the receiver and applier threads of a channel have stopped, in either order, the feature must reset the queue (referred to as queue reset in this document): (1) drop all envelopes, (2) delete the dropped transactions' spill files, (3) zero the cursors and the memory-usage counter, and (4) clear `Retrieved_Gtid_Set`.
- FR27.1. On the next IO thread start, every unapplied transaction must be re-fetched by GTID auto-positioning from `gtid_executed`.
- FR28. On a server restart or crash, the queue is destroyed with the process. At the next startup, the server must delete leftover spill files, and the channel recovers by GTID auto-positioning from `gtid_executed`.
- FR29. On `STOP REPLICA SQL_THREAD` only (the receiver keeps running), all uncommitted transactions in the worker session pool are rolled back. The queue must retain every uncommitted transaction envelope with its payload intact and must keep the current `Retrieved_Gtid_Set`.
- FR29.1. On `START REPLICA SQL_THREAD` after `STOP REPLICA SQL_THREAD`, the applier must reset the dispatch cursor to the head of the queue (where the commit cursor is), reconstruct the `Job_applier` objects, and re-dispatch all retained uncommitted transactions in order from the queue head. Committed transactions are skipped based on the envelope status.
- FR30. On `STOP REPLICA IO_THREAD` only (the applier keeps running), the IO thread must truncate the current in-progress open transaction, and stop immediately without affecting the SQL thread. The SQL thread is not interrupted by the IO thread stop and continues applying all fully received transactions in the queue. If a truncated transaction exists, the worker stops executing once it receives the truncate signal and rolls back any applied changes.
- FR30.1. On `START REPLICA IO_THREAD` after `STOP REPLICA IO_THREAD`, the receiver must automatically re-fetch the previously truncated transaction based on GTID auto-positioning, so the applier can re-dispatch and re-apply the transaction.
- FR30.2. The queue must treat a truncated envelope as a terminal state. When a truncated envelope reaches the head, the sweep advances the commit cursor over it, removes it from the queue, and frees its reserved memory on destruction.
- FR31. On `RESET REPLICA`, the feature must perform queue reset and delete any spill files. `gtid_executed` is left unchanged, so `START REPLICA` can re-fetch by GTID auto-positioning.
- FR32. The feature must add its per-channel metrics as new columns in the existing `performance_schema.replication_applier_metrics` table, which has one row per channel. For the full list of fields, refer to the High Level Design: Observability section.
- FR32.1. The metrics are kept in memory and are not persisted. Cumulative in-memory relaylog columns track the transactions completed in the current applier run, including transactions skipped because their GTID was already executed. They reset when the applier restarts, and read 0 while the applier is stopped or if applier metric collection was off when the applier started. The byte counters sum the transaction size declared in the GTID event, which is the compressed size for a compressed transaction. Current-value columns read 0 after the channel fully stops.
- FR32.2. `replication_applier_metrics` is provided by `component_replication_applier_metrics`, so the new columns are visible only while that component is installed.
- FR33. The feature must expose its per-channel configuration in `performance_schema.replication_applier_configuration`. The values must reflect what `CHANGE REPLICATION SOURCE TO` set and be persisted with the other in-memory relaylog settings. Runtime metrics remain in the separate `replication_applier_metrics` table (FR32).
- FR34. The feature must add the following columns to `SHOW REPLICA STATUS`. Each shows the channel's current value, and 0 for a channel that does not use the feature. After the channel fully stops, all read 0, because the queue and its spill files are discarded (FR27).
  - `In_Memory_Relay_Log_Space`: bytes currently reserved by memory path transactions.
  - `In_Memory_Queue_Length`: number of transaction envelopes currently in the queue.
- FR35. Receiver-side (IO thread) and queue-side (in-memory queue) errors introduced by the feature must be reported through the standard receiver error channel `SHOW REPLICA STATUS` (`Last_IO_Errno` / `Last_IO_Error` / `Last_IO_Error_Timestamp`) and the server error log, exactly as IO-thread errors are reported today.
- FR36. The memory path must populate `performance_schema.replication_applier_status_by_worker` (`LAST_ERROR_NUMBER`, `LAST_ERROR_MESSAGE`, `APPLYING_TRANSACTION`) in the same manner as the existing CSA design, so that failing transactions are identified by their GTID.
- FR37. If the feature encounters a non-recoverable error, the user must be able to fall back to the standard disk path relaylog and resume replication without data loss.
- FR38. To disable the feature on a channel, the user must stop both the receiver and applier threads, then run a CRST statement that either sets `IN_MEMORY_RELAYLOG_ENABLED = OFF` or switches the channel to MTA (`APPLIER_VERSION = 1`).
- FR38.1. When the feature is disabled, the server must perform queue reset, destroy the channel's in-memory queue object, and delete the channel's spill files. On the next `START REPLICA`, the channel must use the disk path relaylog. Transactions that were in the queue but not applied are fetched again by GTID auto-positioning from `gtid_executed`.
- FR38.2. When the feature becomes active on a channel, the server must purge the channel's relaylog files and clear `Retrieved_Gtid_Set`.

### Non-Functional Requirements

- NFR1. The feature must produce the same replication result as the disk path relaylog.
- NFR2. The feature must produce the same recovery result regardless of the lifecycle events the server experiences, such as STOP/START REPLICA, server restart, or crash.
- NFR3. In recovery, the feature must use the same mechanism and reach the same outcome as a normal GTID-based replica (re-fetch by GTID), so that existing operational procedures continue to apply unchanged.
- NFR4. Channels that do not enable the feature must see no change in behavior, code path, or performance.
- NFR4.1. The worker decode and execution path must not change. Workers must receive the same event byte stream as the disk path relaylog.
- NFR5. Operators must account for the additional disk space used by the spill files under `#in_memory_relaylog_temp_files`. `relay_log_space_limit` bounds the declared size of the spill path transactions (FR20). The files on disk are slightly larger, because of the relaylog header. `SPILL_BYTES_USED` shows the actual size.
- NFR6. A transaction envelope is accessed concurrently by the receiver (appending events), the coordinator (dispatching it), and a worker (applying it); all of this concurrent access must be correctly synchronized, with no data races.
- NFR7. When parallel workers commit transactions out of source order (`replica_preserve_commit_order=OFF`), the queue and the memory-usage counter must stay consistent. There must be no entry corruption, no lost or double-swept slots, and no miscounted bytes during the commit process.
- NFR8. `STOP REPLICA` with in-flight jobs must be safe. It must not leak a payload's memory, free a payload twice, or leave a transaction applied halfway without rollback.
- NFR9. All of the feature settings are per-channel and persisted, following standard `CHANGE REPLICATION SOURCE TO` semantics. Options can only be configured while replication is stopped, take effect the next time the channel starts, and survive a server restart.
- NFR10. The feature must remain compatible with existing clients, replicas, and tooling, and must not weaken data security. The feature does not alter the replication contents, and leaves the source, downstream replicas, and binlog/source tooling unaffected.
- NFR11. The feature must not require any change to the client-server or replication protocol.
